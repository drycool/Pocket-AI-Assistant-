# Уроки Llamafile для admin-stick

Разбор 13.11.2026 по обзору Gemini «Обзор Llamafile для личного использования»
(`~/Downloads/Gemini-…-20261113-1555.md`) и по тому, что уже лежит в этом репозитории.
Обзор — пересказ README проекта, поэтому его утверждения сверялись с кодом, а не
принимались на слово. Llamafile — проект Mozilla Builders (Justine Tunney): llama.cpp +
Cosmopolitan, один исполняемый файл, встроенный веб-сервер и OpenAI-совместимый API.

## Что подхода Mozilla действительно правильно

1. **Один самодостаточный артефакт.** Запустил файл — работает: модель, сервер, UI.
   Ни установки, ни зависимостей, ни «а ещё нужен curl».
2. **Память — отдельный сервис.** У самого Llamafile сквозной памяти нет, и это честно:
   модель не помнит ничего между сессиями, память — задача внешнего слоя (RAG/роутер).
3. **Агентские инструменты декларативны.** `read_file`, `write_file`, `grep_search`,
   `file_glob_search`, `exec_shell_command`, MCP — модель просит инструмент, а не пишет
   команду в Markdown, которую потом разбирают регуляркой.
4. **Локальный API вместо привязки к UI.** Любой клиент (Page Assist, Open WebUI, IDE)
   подключается к `127.0.0.1:8080/v1` — интерфейс сменный, ядро одно.

## Что в admin-stick уже есть (и не требует переделки)

| Возможность Llamafile | Что у нас |
|---|---|
| Один бинарник, без зависимостей | `agent.exe` / `fastagent.exe` на Go, только stdlib |
| OpenAI-совместимый API | клиент `sendMessage` к `/v1/chat/completions` + нативный Gemini |
| Локальная модель | Ollama на gpu2 через Pi-шлюз (WoL, прогрев) |
| Нулевой след на чужом ПК | Firefox Portable с изолированным профилем, данные только на флешке |
| Память как внешний слой | Jev-роутер (FTS5 + материал + синтез), LightRAG-граф по запросу |
| Выполнение команд с контролем | FastAgent L0–L3, подтверждения, журнал `actions_*.log` |
| Отчёты | `/report` → Markdown в `Data/reports/` |

## Чего нет — и это настоящие пробелы

1. **Самодостаточность нарушена там, где нужнее всего.** RAG-путь до сегодняшнего дня жил
   в `scripts/rag_query.bat` и требовал `curl` + `jq` на гостевом ПК. На чужом ноутбуке
   их может не быть — «память» молча перестаёт работать, и это худший вид дефекта:
   тихий.
2. **Нет встроенного сервера и UI.** Только консоль. Llamafile открывает браузер — админу
   на выезде это удобнее, а Firefox Portable у нас уже на флешке.
3. **Инструменты не декларативны.** Команды вынимаются из ```-блоков ответа регуляркой
   (`extractCommands`). Модель, оформившая команду иначе, просто не будет услышана.
4. **Память не встроена в сессию.** Батник — отдельная утилита: спросил, прочитал, дальше
   сам. Найденная справка не попадает в историю модели автоматически.

## Что берём (решения)

### Этап 8 — слой знаний внутри бинарника (сделано 13.11.2026)

`FastAgent/rag.go`: тот же запрос к Jev, что делал `rag_query.bat`, но `net/http` без
`curl`/`jq`. Команды `/rag <вопрос>` и `/rag graph <вопрос>`; найденная справка уходит в
историю как `Справка из базы знаний (…)`, поэтому модель отвечает с её учётом.
`execute:false` — режим «только материал» (поле `context`), честно быстрый.
Семь тестов на контракт с роутером (`rag_test.go`): execute/material/graph/HTTP-ошибка/
пустой ответ/метастрока. Граф не включается автоматически — замер 22.09.2026 показал,
что на мануале он медленнее и отвечает не по теме.

### Этап 9 — `fastagent.exe --serve`: API + встроенный UI

- `GET /` — встроенная (embed) страница чата: поле вопроса, история, кнопки «диагностика»,
  «отчёт»; без внешних JS-библиотек, работает в Firefox Portable.
- `POST /v1/chat/completions` — OpenAI-совместимый endpoint, чтобы к агенту можно было
  подключить Page Assist/Open WebUI, как к Llamafile.
- По умолчанию слушает `127.0.0.1`, доступ по токену из конфига; **в HTTP-режиме команды
  не выполняются** (только чат + диагностика чтением). Иначе любой в LAN получил бы
  исполнение команд на чужом ПК. Выполнение — только в консоли, где оператор видит
  подтверждения.
- Это и есть «запустил один файл — открылся интерфейс», но без 2–8 ГБ модели внутри.

### Этап 10 — декларативные инструменты и MCP

- `read_file`, `grep_search`, `file_glob_search` — L1 (чтение, без спроса);
  `write_file` — L2+ с подтверждением и записью в журнал.
- Извлечение вызовов — не только ```-блоки, но и JSON-конверт (`{"tool":…,"args":…}`),
  чтобы модель могла просить инструмент структурно.
- MCP-клиент (stdio) — подключение внешних серверов без пересборки агента. Jev уже умеет
  отдавать знания по HTTP; MCP даст тот же путь другим инструментам.

### Этап 11 — память между сессиями

- Локальный кэш справок (`Data/rag-cache/`) — офлайн-повторные вопросы без сети.
- Экспорт уроков сессии в корпус (только по явной команде оператора: гостевой ПК —
  не место для автоматической утечки данных).
- Вердикты `jev_feedback` по `decision_id` из `/rag` — чтобы база знала, был ли ответ
  полезен (сейчас decision_id только печатается).

## Что не берём и почему

- **GGUF-модель внутри exe.** 2–8 ГБ на флешке и минуты загрузки; у нас модель уже есть
  на gpu2, а на чужом ПК без сети Ollama всё равно не поднять. Один файл — да, модель
  внутри — нет.
- **Cosmopolitan C.** Go и так даёт статический бинарник под Windows; второй тулчейн не
  нужен.
- **GPU-бэкенды (CUDA/ROCm/Metal).** Не наша поверхность: инференс на gpu2.

## Честные ограничения

- Обзор Gemini рекламный: «локальная LLM за 10 секунд» верно только если файл с моделью
  уже скачан; скорость — это скорость llama.cpp, не магия.
- Tool calling реален только для моделей, обученных ему; DeepSeek и qwen3 поддерживают
  частично, и проверять это надо на живых прогонах, а не по README.
- Встроенный сервер на чужом ПК — поверхность атаки. Поэтому localhost + токен + запрет
  exec в HTTP-режиме; это ограничение, а не «пока не сделали».
