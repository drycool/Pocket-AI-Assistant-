ПОЛЕВОЙ ТЕСТ УДАЛЁННОЙ ДИАГНОСТИКИ (R1–R4)
==========================================
Версия: сборка 18.11.2026 (R4: архив сессии, journal/save, /fb).
Что проверяем: гость на Windows сам звонит на брокер pi5, оператор работает
в своём терминале; в конце сессии остаются два файла — txt-архив и уроки
в память Jev. Всё остальное (diag, read, run, get/put) — регрессия R1–R3.

Кто где:
  pi5     — брокер + консоль оператора (linux/arm64);
  Lenovo  — гость, Windows (fastagent.exe с флешки).

---------------------------------------------

Сравнить с первой строкой SHA256SUMS.txt (fastagent.exe). Должно совпасть.
Если не сходится — exe старый, тест ничего не проверит: перезаписать с pi5.

2) СЕТЬ: БРОКЕР НА pi5 (2 мин)
------------------------------
Маршрут наружу уже настроен и проверен 18.11.2026:
  https://pi5.tail823290.ts.net/fa  ->  http://127.0.0.1:8866
  (tailscale funnel: /fa proxy 127.0.0.1:8866; funnel срезает префикс,
   поэтому гость зовёт /fa/pair, а брокер видит /fa/pair — сходится.)
Проверка: sudo tailscale funnel status | grep -A1 '/fa proxy'

Терминал 1 (pi5, из корня admin-stick):
  ./FastAgent/fastagent -broker -broker-addr 127.0.0.1:8866 \
      -broker-secret S3CRET -ticket-exe FastAgent/fastagent.exe
ВАЖНО: секрет обязателен, даже если брокер слушает loopback: funnel приходит
к брокеру с 127.0.0.1, и без секрета операторские ручки стали бы публичными.

В терминале 1 (оператор): [OK] Гость на связи.

5) ЧЕК-ЛИСТ КОМАНД (по порядку, в терминале 2)
----------------------------------------------
  help                       -> справка, шагом не считается
  diag                       -> системные данные, шаг 1
  read C:\Windows\win.ini    -> содержимое, шаг 2
  run ipconfig /all          -> чтение, БЕЗ y/n, шаг 3
  run echo R4>C:\Users\Public\fa-r4.txt
                             -> вопрос «Запустить? (y/n)», ответ n
                                «Отменено оператором», шаг 4
  run ipconfig /flushdns     -> вопрос, ответ y -> код 0, шаг 5
  journal 30                 -> host=<имя>, path=<...\actions_remote_*.log>,
                                lines=N, затем хвост с approved=true/false
  save Lenovo R4: сеть/архив — что проверили и что вышло
                             -> путь remote-<код>-<дата>.txt и remote-<код>-<дата>.md
  quit                       -> гость: «[link] оператор закрыл сессию — выхожу.»
Ожидаемый счёт: «Шагов: 5» (diag, read, run, run, journal).
Служебный забор журнала перед save/quit шагом НЕ считается.

6) АРХИВ: ЧТО ПРОВЕРИТЬ НА pi5 (5 мин)
--------------------------------------
  ls -l Data/logs/remote-<код>-*.txt          # обычно 15–40 КБ
  ls -l /home/dry/memory/projects/remote-<код>-*.md
В txt:
  шапка (гость, длительность, шагов, отказов, файлов);
  лента сессии с ответами гостя;
  «журнал гостя» с вердиктами: approved=false у echo> и approved=true у flushdns.
В md — разделы ровно второго уровня (их режет чанкер Jev):
  ## Что это | ## Ход сессии | ## Отказы и ошибки |
  ## Журнал гостя (verdict / approved) | ## Заметка оператора
Главная регрессия 18.11.2026: заметка из `save` должна остаться и после `quit`
(раньше выход затирал её пустой строкой). Проверить: grep -A3 'Заметка' файл.md

7) ПАМЯТЬ И /fb (10 мин)
------------------------
  python3 /home/dry/Jev/scripts/index_feeds.py --feed memory
  # проверка: спросить базу о сессии
  # (jev_query "Lenovo R4") -> в ответе должен быть новый документ.
/fb — вердикт по последнему /rag (в консоли FastAgent, уровень L1):
  /rag как сбросить кэш DNS в Windows
  -> ответ Jev + decision_id
  /fb accepted
  -> [OK] вердикт записан в Jev: accepted
Если роутер журнал решений уже ротировал — будет честное «decision_id не
найден», это не сбой.
