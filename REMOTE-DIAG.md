# Сценарий «удалённая диагностика»: гость звонит на Pi, оператор держит ключи

Проектная записка, 17.11.2026. **R1–R4 реализованы 18.11.2026**: R1–R3 проверены живой парой
брокер↔гость↔оператор на pi5 (см. §7a, §7b и §7c), R4 — код, тесты и разбор гостевого журнала
(§7d); живой прогон R4 на Lenovo — за оператором. Продолжает линию
`FIELD-TEST.md` / `LLAMAFILE-LESSONS.md`.

## 1. Что происходит сейчас

Оператор подключается к проблемному ПК по AnyDesk и дальше **печатает команды в чужое окно**:
диагностика, `sfc`, `dism`, `wevtutil`, чтение логов. Три беды:

- набирать в AnyDesk долго и хрупко: раскладка (en/ru) переключается в чужой системе,
  автодополнение и история — чужие, одна опечатка в `wevtutil` стоит минуты;
- результаты остаются на гостевом ПК в консоли; чтобы их прочитать, оператор их листает
  через тот же AnyDesk, копирует обрывками;
- ключ модели лежит на флешке и, значит, на гостевом ПК; модель и справка (Jev) — не под рукой.

## 2. Инверсия направления

Не «я влезаю на гостя и стучу по клавишам», а «**гость сам звонит на pi5**, а я работаю в своём
терминале». На гостевой ПК попадает ровно один файл — `fastagent.exe`, уже умеющий говорить с
брокером. Дальше все команды, чтения, отчёты и подтверждения идут через эту сессию, а
AnyDesk нужен только чтобы перетащить файл и запустить его (и для GUI-починок).

```
┌──────────────┐   drag-and-drop   ┌────────────────────────┐
│ pi5 (оператор)│  fastagent-a1b2c3.exe │ гость за NAT, AnyDesk │
│               │ ────────────────▶ │  двойной щёлчок        │
│ fastagent     │                   │  fastagent.exe -link   │
│ -remote a1b2c3│ ◀── HTTPS 443 ─── │  (звонит НАРУЖУ)      │
└──────┬───────┘   (Tailscale Funnel)└────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────┐
│ брокер на pi5: https://pi5.tail823290.ts.net/fa │
│ пара «код → сессия», длинный поллинг, TTL     │
└──────────────────────────────────────────────┘
```

Почему наружу звонит гость: за NAT и корпоративным файрволом открывать порт не нужно, а Funnel на
pi5 уже включён (`tailscale funnel status`: `https://pi5.tail823290.ts.net:10000`, `:8443`, 443) —
значит у нас валидный сертификат и адрес, доступный из любой сети без установки Tailscale.

## 3. Файл-билет

Кода ввода нет. Оператор на pi5 делает `fastagent -remote new` — брокер создаёт сессию `a1b2c3`
и кладёт рядом копию бинаря `fastagent-a1b2c3.exe`. Этот файл перетаскивается в окно AnyDesk
(файл-трансфер, без набора текста). Гость дважды щёлкает — бинарь читает **своё имя**, берёт код,
зовёт `/pair`, получает сессионный токен и начинает поллинг. Если имя переименовали — спросит код
в консоли. Одна строка на гостевой стороне, и та не набирается.

## 4. Протокол: stdlib, без внешних зависимостей

`go.mod` у FastAgent пустой (`module fastagent`), и это правило не ломаем: ни WebSocket-библиотек,
ни MQTT. Длинный поллинг + SSE на `net/http` даёт задержку меньше секунды и переживает прокси.

```
POST /fa/session            (оператор)  → {code, op_token}      создать сессию
POST /fa/pair               (гость)     → {guest_token}          по коду, окно 15 мин
GET  /fa/poll?wait=25       (гость)     → {id,kind,args} | 204   длинный поллинг 25 с
POST /fa/result             (гость)     → 200                    {id,ok,out,exit,ms}
POST /fa/cmd                (оператор)  → 202                    поставить команду в очередь
GET  /fa/events             (оператор)  → SSE                    результаты и статус
POST /fa/close              (оба)       → 200                    завершить
GET  /fa/ticket/{code}.exe  (публично)  → бинарь с кодом в имени  файл-билет
```

`kind` — те же пути, что уже есть в агенте: `diag`, `read_file`, `grep_search`,
`file_glob_search`, `write_file`, `run` (команда). Аргументы — тот же JSON, что у декларативных
инструментов этапа 10, поэтому на гостевой стороне ничего нового классифицировать не надо:
запрос проходит через `classify()` и `logAction()` как обычный.

Размер по факту R1: брокер+подпись — `remote.go` 625 строк, гость — `remote_link.go` 265,
консоль — `remote_console.go` 386, тесты — `remote_test.go` 432 (9 тестов). Оценка была
~600 строк; вышло 1 276 — разница в мелочах, без которых канал не живёт: переподключение SSE,
повтор пары, лимит размера результата, файл-билет.

## 5. Безопасность: три вещи, которые нельзя сломать

Проект уже отказался от исполнения команд по HTTP (`serve.go`: «в HTTP-режиме команды НЕ
выполняются»). Удалённый режим — сознательное исключение, и у него свои замки.

1. **Ключа модели на госте нет.** Модель (DeepSeek/Jev) работает на стороне оператора; гость
   передаёт только результат команды. На флешке ключ нужен для автономного режима, в удалённом —
   нет, и в конфиг гостя он не попадает.
2. **Сквозная подпись.** Сессионный ключ выводится из кода и guest-токена (`HMAC-SHA256`), команды
   подписываются на стороне оператора и проверяются на госте. Брокер — только реле: даже если его
   скомпрометируют, подделать команду он не сможет, потому что ключа не знает.
3. **Политика и подтверждения остаются на госте.** `classify()` решает локально; L2+ выполняются
   только при `approved:true`, который консоль оператора ставит после y/n, набранного **у оператора**,
   и который входит в подпись (R2).
   Агент на госте отказывает при любом расхождении — даже если консоль ошиблась. Автоподтверждения
   нет ни в одном режиме, модель не может «попросить» его включить: флага не существует.

Дополнительно:

- сессия одноразовая: max 2 ч, простой 15 мин, `close` любой стороной; токен только в памяти,
  на диск не пишется, автозапуска и службы нет — закрыл процесс, следов не осталось;
- журнал: `Data/logs/actions_remote_<штамп>.log` — `provenance=remote op=<id> cmd=… verdict=…
  approved=…`; копия сводки у оператора;
- что запрещено по конструкции: reverse shell, автоисполнение по ответу модели, персистентность,
  приём команд от кого-либо кроме парной консоли (код+токен+HMAC).

## 6. Что получает оператор

- свой терминал с историей, автодополнением и нормальной раскладкой — вместо чужого окна AnyDesk;
- `/rag` и локальную модель **до** куда-либо идущих запросов: справка из Jev про этот же дефект
  приходит из своей памяти, а не из интернета;
- инструменты этапа 10 (`read_file`, `grep`, `glob`) — то есть «покажи мне hosts, покажи события
  за сутки, найди все config.ini» выполняются без набора по буквам;
- всё уходит в `Data/logs/` на pi5 и, если захотим, в Jev — уроки сессии не теряются;
- один и тот же режим работает и для своего ПК (127.0.0.1), и для гостя: разницы в интерфейсе нет.

## 7a. Что сделано в R1 (18.11.2026)

Код: `FastAgent/remote.go` (брокер, ключ и подпись), `remote_link.go` (гость), `remote_console.go`
(консоль оператора, файл-билет), `remote_test.go` (9 тестов). Ветка `feature/deepseek-fast-agent`.

Флаги (все — в одном бинаре, как и остальные режимы):

| команда | кто | что делает |
|---|---|---|
| `fastagent -broker -broker-addr 127.0.0.1:8866 -broker-secret S -ticket-exe fastagent.exe` | pi5 | слушает `/fa/*`; без секрета — только loopback (проверяется при старте) |
| `fastagent -remote new -broker-url URL -broker-secret S [-ticket-exe fastagent.exe] [-remote-cmd "diag"]` | оператор | создаёт сессию, печатает код, кладёт `~/.cache/fastagent/fastagent-<код>.exe`, ждёт пары 15 мин, затем REPL |
| `fastagent-<код>.exe -link [-broker-url URL]` | гость | код берётся из имени файла; если имя переименовали — спросит код в консоли |

Консольные команды R1: `diag`, `read <путь>`, `grep <шаблон> [каталог] [glob]`,
`glob <шаблон> [каталог]`, `help`, `quit`. Других глаголов нет — `run`/`write_file` в R1 не
существует ни в консоли, ни на госте (`TestRemoteExecOnlyRead`: `classifyTool(kind, L1Read)`
не пускает дальше чтения, отказ пишется в журнал с вердиктом).

Проверено живой парой на pi5 (18.11.2026, три сессии):
- `diag` → результат за **0.07 с** (ядро, uptime, память, диски, сеть, журнал);
- `read /etc/hostname` → `1: pi5` за 0.00 с;
- файл-билет: `GET /fa/ticket/<код>.exe` отдал 9 000 174 байта с
  `Content-Disposition: attachment; filename="fastagent-<код>.exe"`;
- журнал гостя `Data/logs/actions_remote_<дата>.log` — записи `link-start`, `diag`,
  `tool:read_file`, все с `provenance=remote`, `approved=true`, `verdict=чтение`;
- `go vet` чистый, `go test ./...` — 105 проверок зелёные.

Отличия от записки (осознанные): отдельной ручки `GET /fa/health` нет — её роль играет
`/fa/ticket` и сам `/fa/pair`; файл-билет на брокере отдаётся **только для существующей сессии**
(иначе сканер перечислял бы коды); `run`/подтверждения у оператора — это R2, в R1 их нет;
L3 в удалённом режиме не планируется (остаётся ответ §10.1).

## 7b. Что сделано в R2 (18.11.2026): `run` и подтверждение у оператора

Гость в удалённом режиме работает на **L2** (если уровень в конфиге ниже — поднимается до L2
с явной строкой в консоли; выше — опускается до L2). L3 удалённо не разрешён: опасное и «вне
белого списка» отклоняется гостем, и `approved` этого не отменяет — это граница режима.

Двухшаговое подтверждение (решает **гость**, спрашивает **оператор**):

1. оператор пишет `run ipconfig /flushdns` → команда уходит с `approved=false`;
2. гость классифицирует её `classify()` и возвращает результат с `needs_approval=true`
   и `verdict=изменение (подтверждение)` — команда **не выполнена**;
3. консоль показывает вердикт и спрашивает `y/n` (для опасного — `yes`) **в терминале оператора**;
4. на `y` уходит та же команда с `approved=true` и **другой подписью**: `approved` входит
   в каноническую строку, поэтому реле не может дописать подтверждение к чужой команде;
5. гость исполняет её через тот же `runCommand` с `commandTimeout` (sfc/dism/chkdsk — 45 мин)
   и пишет в журнал `approved=true`; консоль ждёт результат до 46 минут и печатает `exit=N`.

Отказ оператора (`n`) ничего не отправляет на гость — команда просто не выполняется; в журнале
гостя остаётся запись «ждёт подтверждения оператора». Автоподтверждения нет: в `-remote-cmd`
без терминала `confirm` честно отказывает.

Границы, проверенные тестами (`TestRemoteExecPolicyOnGuest`, всего 105 проверок):
чтение через `run` (`id`, `uname -a`) — без вопросов; `ipconfig /flushdns` без `approved` —
`needs_approval`; с `approved` — выполняется; `rm -rf /`, `format C:` — отказ на L2 даже
с `approved`; `write_file` удалённо по-прежнему не выполняется.

Живой прогон 18.11.2026 (pi5, три сессии):
- `run uname -a && id` → `exit=0`, 0.01 с, без вопроса (чтение);
- `run ipconfig /flushdns` + `y` → вердикт «изменение (подтверждение)», `exit=127`
  (`/bin/sh: ipconfig: not found` — это Pi, не Windows), в журнале `approved=true`;
- `run netsh winsock reset` + `n` → «Отменено оператором: команда на госте не выполнена»,
  в журнале только «ждёт подтверждения оператора».

Дефект, найденный прогоном и исправленный: журнал писал `approved:false` у выполненной после
`y` починки, потому что флаг выводился из вердикта (`verdict == VReadOnly`). Теперь `approved`
передаётся явно из подписанной команды.

## 7c. Что сделано в R3 (18.11.2026): передача файлов кусками

Файлы ходят теми же подписанными командами, отдельного протокола нет: два новых `kind`
(`get_file`, `put_file`), кусок — 256 КиБ, лимит файла — 50 МиБ. Результат получил поля
`data` (base64), `offset`, `total`, `eof`, `sha256`; брокер ограничивает JSON результата 1 МиБ
и **не хранит** `data` в карте сессии (карта ограничена 256 записями), иначе передача файла
оставляла бы в памяти реле копию всего файла.

**`get` — забрать файл.** Гость читает кусок по `offset` и проходит те же запреты, что
`read_file`: секреты, каталоги, лимит 50 МиБ. В первом куске приходит `sha256` всего файла.
Консоль складывает куски в `~/.cache/fastagent/incoming/` (если такой файл уже есть — рядом
появляется `-1`, `-2`: принятый файл не затирается), пишет во временный `.part` и
переименовывает только после сверки размера и хеша.

**`put` — положить файл.** Это запись, поэтому путь как у `run`: гость классифицирует
операцию (`classifyTool("write_file")` → на L2 «изменение»), и **без `approved` не пишет ни
байта** — отвечает `needs_approval` с вердиктом. Консоль спрашивает `y` в терминале
оператора, и только потом куски уходят с `approved=true` (другая подпись). Гость пишет в
`<цель>.part-fastagent` с проверкой `offset`, в конце выравнивает размер, сверяет `sha256`
всего файла и переименовывает. Недописанный или подменённый файл под настоящим именем не
появляется. Системные каталоги и секреты отклоняются даже с `approved`.

Команды консоли: `get <путь на госте> [локальный путь]`, `put <локальный> <путь на госте]`
(в `-remote-cmd` тоже работают). Куски идут последовательно, по 256 КиБ, поэтому канал
занимает одна передача; прогресс печатается одной строкой.

Живой прогон 18.11.2026 (pi5, брокер + гость + консоль):

- `get /etc/hostname /tmp/r3/hostname.copy` → 4 Б, `sha256` сверен, файл получен;
- `put /tmp/r3/up.bin /tmp/r3/guest-up.bin` → гость: `needs_approval`; `y`; **3 145 728 байт
  за 3.0 с** (12 кусков по 256 КиБ, ~1 МиБ/с на loopback при интервале поллинга 200 мс);
  `sha256` на госте совпал с исходным до байта; в журнале — 12 записей `put_file … approved=true`
  и итоговая «записано 3145728 байт»;
- отказ (`n`) на втором `put` → «Отменено оператором: файл на госте не записан», файла нет,
  в журнале гостя одна запись `approved=false` «ждёт подтверждения оператора».

Дефекты, найденные прогоном и исправленные:

1. консоль отдавала `kind` `get`/`put` вместо `get_file`/`put_file` (не сработал маппинг
   `verbToKind`) — гость справедливо отказывал «недоступно удалённо»;
2. после успешной записи консоль печатала результат **первого** ответа «нужно подтверждение»:
   `res, ok :=` внутри цикла затенял внешние переменные, наружу уходил старый результат;
3. файл-билет не включал режим гостя: двойной щёлчок по `fastagent-<код>.exe` открывал
   обычный агент (проверки имени не было) — теперь имя `fastagent-<6 hex>` само включает
   `-link`, как и было обещано в §3.

Проверки: 107 тестов, из них `TestRemoteGetFileChunks` (куски, `eof`, хеш, отказы на секрет/
каталог/лимит/`offset`), `TestRemotePutFileApprovalAndChecks` (без `approved` файла нет,
с `approved` пишется, неверный `sha256` не оставляет файла, `/etc` и секреты отклонены),
`TestRemoteFileTransferThroughBroker` (полный круг через брокер: `get`, `put` с `y`, `put` с `n`).

## 7d. Что сделано в R4 (18.11.2026): архив сессии и уроки для Jev

Смысл R4 — «чтобы следующий такой случай был дешевле». Удалённая сессия исчезает вместе с
терминалом, а ценное в ней — что спросили, что ответил гость, **какие вердикты вынесла его
политика** и чем это кончилось. Вердикты и `approved` живут только на госте, поэтому архив
собирается из двух источников: консоль записывает каждый свой шаг, а у гостя отдельной
командой забирается хвост его журнала. Модель здесь не участвует: домысленные выводы живут
в общей памяти дольше, чем стоит.

**Две ручки консоли** (работают и в REPL, и в `-remote-cmd`):

| команда | что делает |
|---|---|
| `journal [N]` | просит у гостя последние N строк его журнала (по умолчанию 200, не больше 1000); это чтение собственного файла и подтверждения оператора не требует |
| `save [заметка]` | забирает журнал гостя, пишет txt-архив и (если задан каталог памяти) уроки; заметка — остаток строки как есть, это текст для людей |

**Два файла.** Имена содержат код сессии и время, поэтому сессии не затирают друг друга:

- `Data/logs/remote-<код>-<ГГГГММДД-ЧЧММСС>.txt` — полный текст для человека: шапка (гость,
  длительность, число шагов, отказов, файлов), журнал сессии как он был в консоли, ответы
  гостя и раздел «журнал гостя» с вердиктами;
- `<память>/projects/remote-<код>-<дата>.md` — уроки в разметке памяти: заголовок первого
  уровня, разделы `## Что это`, `## Ход сессии` (таблица шагов), `## Отказы и ошибки`,
  `## Журнал гостя (verdict / approved)`, `## Заметка оператора`. Чанкер Jev режет документ
  по `## `, поэтому разделы именно второго уровня.

**Каталог памяти — только явно.** Флаги: `-memory-dir` (по умолчанию `JEV_MEMORY_DIR`),
`-jev-dir` (по умолчанию `JEV_HOME` или `/home/dry/Jev`), `-reindex` (пересобрать FTS5 и
вектора после записи). Пустой каталог памяти — это «только txt, в общую память ничего не
пишем»: именно так надо вести сессию на чужой машине и на Windows-госте, где Jev нет вовсе.
Без `-reindex` консоль печатает обе команды индексации, а не делает вид, что память уже
знает новый файл.

**Порядок с журналом гостя.** Хвост забирается **до** закрытия сессии: после `close` гость уже
не ответит, и вердикты пропали бы бесследно — ровно то, ради чего R4. Поэтому `quit` в
консоли сначала тянет журнал, потом закрывает сессию, и только после выхода пишет архив.
Ответ гостя начинается строками `host=`, `path=`, `lines=`, дальше `---` и сам хвост: оператор
видит, у кого именно он снимал диагностику и где на госте лежит полный журнал (его можно
забрать через `get`). Команда идёт тем же подписанным каналом, что и остальные, — отдельного
протокола у R4 нет; вывод журнала обрезается до 64 КиБ, как любой результат гостя.

**Экспорт `jev_feedback`.** Справка `/rag` теперь запоминает `decision_id` и вопрос, а `/fb
accepted|partial|rejected [комментарий]` отправляет вердикт в роутер (`POST /feedback`,
`source=human`). Вопрос уходит вместе с вердиктом, потому что роутер хранит только хеш
вопроса и без текста вердикт читателю ничего не скажет. Если роутер не знает `decision_id`
(журнал решений ротировался), это печатается, а не выдаётся за успех.

**Границы.** Один шаг попадает в txt не длиннее 24 КиБ (гость и так режет ответ до 64 КиБ):
архив открывают в блокноте, и «…обрезано» остаётся честной пометкой. В уроки попадает до 40
отказов, журнал гостя — до 4 000 символов на раздел. Автоподтверждений и «сохранений на
выходе без ведома оператора» нет: архив пишется после `quit`, после `-remote-cmd` и по
`save`, а уроки в память — только при заданном каталоге памяти.

**Проверки: 118 тестов**, из них 11 новых в `session_archive_test.go`:
`TestArchiveTextAndLessons` (оба файла и разделы уроков), `TestArchiveTextTruncatesLongOutput`
(пометка об обрезке), `TestTailLines`, `TestTruncateNote`, `TestParseRemoteCommandJournalSave`
(`journal [N]`, `log`, `save`/`archive` с заметкой и без), `TestLinkJournalTail` (`host=`/
`path=`/`lines=`, хвост, отсутствие журнала — честная ошибка), `TestSaveArchiveWritesFiles`
(txt и md на месте, без каталога памяти — только txt), `TestPostJevFeedback` (поля запроса,
разбор ответа, пустой `decision_id`, неизвестный вердикт, HTTP-ошибка),
`TestRemoteJournalThroughBroker`, `TestRemoteSaveThroughBroker` (полный круг через
брокер: журнал гостя, `save`, архив и уроки) и `TestSaveArchiveKeepsNoteAcrossExitSave`
(заметка не теряется на выходе).

Дефекты, найденные прогонами и исправленные:

1. `truncateNote` резала текст по байту и проверяла только висячее продолжение UTF-8 —
   «я» на 21-м байте оставляла в файле байт `0xD1`. Теперь последняя руна проверяется
   `utf8.DecodeLastRuneInString` и обрезается целиком (тест `TestTruncateNote`);
2. выход после `save заметка` писал архив ещё раз — с **пустой** заметкой, и раздел
   «Заметка оператора» в уроках затирался. Теперь заметка последнего сохранения хранится в
   архиве (`lastNote`) и выход её не теряет (тест `TestSaveArchiveKeepsNoteAcrossExitSave`);
3. служебный забор журнала (перед `save` и `quit`) попадал в ленту шагом и надувал
   «Шагов: N». Теперь журнал хранится отдельным полем архива, а шагами остаются только
   команды оператора.

## 7e. Что сделано в R5 (18.11.2026): регламент сессии и меню оператора

Смысл — убрать терминал из живой сессии. Оператор в AnyDesk с клиентом не
набирает `sudo`, `powershell -c` и пути к журналам: файл клиенту передан в
начале сессии, дальше — меню и одно действие на регламент. Регламент — это
данные (`scenarios/*.json` рядом с бинарём), а не код: новая проверка
добавляется текстом, пересборка не нужна.

**Меню после пары** (`-remote new`, если не задан `-plain`):

```
 1  Старт: эталон файла, секреты, журнал гостя
 2  Диагностика: Стандартная диагностика Windows (13 проверок)
 3  Починки (6)
 4  Отчёт: архив, уроки, контроль секретов
 5  Выход
```

Пункт 1 выполняется **сразу после пары** и не пропускается: пока он не
пройден, пункты 2–3 заблокированы. Это и есть «перечень необходимого, через
который не перешагнуть»:

| проверка | что значит |
|---|---|
| эталон файла | размер и sha256 файла, который ушёл клиенту, против `scenarios/manifest.json` (пишется при сборке) |
| секреты в файле | в exe ищутся точные значения ключей из рабочего конфига; в отчёт попадает имя провайдера, не значение |
| журнал гостя | путь, размер, строки и «чисто» (нет ли ключей в журнале, который остаётся на машине клиента) |
| архив и уроки | те же проверки по тексту архива **до** записи в общую память: при находке txt пишется, уроки — нет |

**Диагностика** идёт одной командой: проверки выполняются последовательно,
на экран — итог, а не простыня. Каждая строка — `[OK] …` или `[!] …` с
числом совпадений; проблемы в конце собраны по приоритету. Полный вывод
команд уходит в архив (R4), поэтому экран остаётся читаемым.

**Починки** — список номеров из сценария: выбор номера, показ команд и одно
подтверждение оператора; дальше команды уходят с `approved=true`, но политика
гостя всё равно проверяет каждую. Без прав администратора честно печатается
код 740 — авто-повышения прав нет.

**Окно клиента** больше не техническое: «Диагностика компьютера», «Связь с
оператором установлена», «окно не закрывайте — в конце оно попрощается само»,
а при закрытии сессии — «Готово. Оператор завершил сессию — закройте это окно».

**Формат сценария** (сокращённо):

```json
{"name":"standard-windows","title":"Стандартная диагностика Windows",
 "checks":[{"id":"errors_system","title":"Ошибки в журнале System","priority":1,
   "timeout_sec":120,
   "commands":["wevtutil qe System /c:40 /rd:true /f:text /q:*[System[(Level=1 or Level=2)]]"],
   "rules":[{"regex":"(?m)^\\s*Level:\\s*[12]\\b","problem_if":"found",
             "message":"критических ошибок: {n}","ok_message":"ошибок нет"}]}],
 "fixes":[{"id":"flushdns","title":"Сбросить кэш DNS","confirm":"Сбросить кэш DNS?",
           "commands":["ipconfig /flushdns"]}]}
```

Правило — регулярное выражение и «проблема, если найдено/не найдено»; `{n}`
заменяется числом совпадений. Модель в оценке не участвует: «положительный
результат» на экране должен быть детерминированным.

**Флаги:** `-scenario standard-windows|standard-linux|<путь>` — выбор
регламента; `-plain` — старая консоль команд (для скриптов и отладки).

**Живой прогон** (pi5: брокер, оператор и гость; гость без флагов, через
Funnel; сценарий `standard-linux`): стартовый блок — эталон совпал (8.8 МиБ,
sha256 `f156fbcb…`), секретов нет, журнал 163 Б — чисто; диагностика 7/7 OK;
отчёт — txt **18 402 Б**, уроки **5 886 Б**, «Шагов: 7», заметка собрана
автоматически; меню и выход по «5» сработали, гость напечатал прощание и вышел.
Найдено и исправлено на прогоне: `systemctl --failed` гость справедливо
заблокировал (нет в белом списке) — в сценарии заменено на `systemctl status
--failed`; пункты меню печатались не по порядку; «1 починок» → «починок 1».

Тесты: **135**, из них 13 новых (`scenario_test.go`, `secrets_test.go`):
загрузка и валидация сценариев, правила found/absent/empty/denied, сверка

## 7f. Запуск без копипасты: `remote.sh` (19.11.2026)

Две команды на два терминала заменены одной обёрткой в корне репозитория
(`remote.sh`, она же функция `remote` в `~/.bashrc`): ей не нужны ни секрет,
ни URL, ни путь к бинарнику.

```
  remote            брокер (если не запущен) + меню оператора
  remote status     что запущено, где секрет, последний файл-билет
  remote stop       остановить брокер
  remote log [N]    хвост журнала брокера
  remote ticket [куда]  путь к свежему файлу-билету; с каталогом — копия туда
  remote clean [N]  оставить N свежих билетов (по умолчанию 3)
```

Что делает `remote`:

1. находит бинарь (`FastAgent/fastagent`, иначе `fastagent-linux-arm64`);
2. берёт секрет из `Data/remote-secret.txt` (при первом запуске генерирует
   случайный и ставит `chmod 600`) — вводить и передавать его не нужно;
3. если `127.0.0.1:8866` свободен — поднимает брокер (`setsid nohup`, журнал
   `Data/logs/broker.log`, PID в `Data/remote-broker.pid`) и ждёт порт до 5 с;
   если занят своим брокером — переиспользует, если чужим (другой секрет) —
   перезапускает;
4. `exec` меню оператора: печатает «Сессия: <код>», «Файл-билет: …» и ждёт
   гостя, как раньше.

**Где файл-билет.** `~` у оператора — домашний каталог (`/home/dry` на pi5),
`.cache` — скрытый каталог (в файловом менеджере `Ctrl+H`). Полный путь:
`/home/dry/.cache/fastagent/fastagent-<код>.exe`, имя = код из строки
«Сессия: <код>». Билет — это копия того же exe, поэтому он создаётся в момент
создания сессии и лежит рядом с билетами прошлых сессий. Отсюда две служебные
команды: `remote ticket` (точный путь, с каталогом — копирование, например на
флешку) и `remote clean [N]` (оставить N свежих, остальные удалить — каталог
за сессии накапливает по ~9 МиБ на файл).

**Дефект файла-билета (19.11.2026) — и почему клиент отвечал «невозможно
запустить это приложение на вашем ПК».** `remote.sh` передавал брокеру
`-ticket-exe "$e"`, где `$e` — локальный linux/arm64-бинарник оператора, на
котором работают брокер и меню. Файл-билет на брокере — это копия именно этого
exe, поэтому клиенту уходил **ELF под именем `.exe`** (9 203 127 Б вместо
6 795 264 Б). Windows на такой файл отвечает `0xc0000033` — «это приложение не
может быть запущено на вашем ПК». Старый флаг, живые прогоны на Lenovo работали,
потому что exe брался с флешки, а не из каталога сборки.

Исправлено в двух местах, чтобы дефект не мог вернуться тихо:

- `remote.sh`: `find_exe` — только локальный Linux-бинарь для брокера и меню,
  новый `win_exe` — только PE (первые байты `MZ`) для `-ticket-exe`
  (`FastAgent/fastagent.exe`, затем `FieldKit/fastagent.exe`); `status` и
  `ticket` предупреждают, если последний билет не PE;
- Go (`remoteTicketFile`): кандидат, который не начинается с `MZ`, пропускается,
  а если PE не нашлось вовсе — сессия не создаётся, ошибка прямо называет файлы
  и причину. Тесты: `TestRemoteTicketFileSkipsNonPE`,
  `TestRemoteTicketFileWritesPE`.

Проверено живьём: после пересборки (manifest windows-exe 6 796 288 Б, sha256
`24b80d4c…`) файл-билет `fastagent-6e5b2e.exe` — `PE32+ x86-64`, sha256 совпал
с `scenarios/manifest.json`.

**Дефект запуска и его причина.** Сначала `remote` была только функцией в
`~/.bashrc`: в уже открытом терминале её нет (`.bashrc` читается один раз при
старте оболочки), и оператор получал `remote: команда не найдена` при полностью
рабочей настройке. Поэтому обёртка теперь существует ещё и как программа в
`PATH`: `~/.local/bin/remote` (каталог добавляется в `PATH` из `~/.profile`,
строка 26) и `/usr/local/bin/remote`; функция в `.bashrc` оставлена и делает то
же самое. Проверено в пустом окружении: `env -i HOME=/home/dry
PATH=/usr/local/bin:/usr/bin:/bin bash -c 'remote status'` отвечает без
`.bashrc`.

Пути считаются от каталога скрипта, поэтому запускать можно из любого каталога.
Журнал брокера и секрет — в `.gitignore`.

Синхронизация флешки тоже одной командой: `bash scripts/sync-flash.sh`
(находит смонтированную флешку по `Data/` и `scenarios/`, кладёт комплект,
обновляет `bin/agent-fast.bat` и копию `FastAgent/`, затем проверяет
`SHA256SUMS` и отказывается «успешно» завершаться при расхождении).

Заодно исправлена раскладка запуска: `bin/agent-fast.bat` и
`scripts/field-test-fastagent.bat` искали exe только в `FastAgent\`, а комплект
на флешке лежит в корне — пункт [6]/[7] меню `START.bat` мог запустить старый
бинарь. Теперь: корень, иначе `FastAgent\`; сценарии всё равно берутся из
`scenarios/` корня (база — два уровня выше exe, рабочий каталог не важен).

| Службы с автозапуском | таблица обрезала `Status` до `ed`, правило `\bStopped\b` молчало — 8 остановленных служб прошли как «ОК» | маркер `STOPPED: имя / отображаемое` |
| Отчёты о сбоях и дампы | считались только `*.dmp`, 30 папок `WER\ReportArchive` дали «ОК» | `CRASH:` по папкам отчётов (до 20) и `DUMP:`, два правила |
| Крупные файлы в профиле | правило отсутствовало — при 7,8 % на C: самое важное оставалось незамеченным | правило «файлов крупнее 500 МБ: {n}», только предупреждение |
| Мало места | только `LOW SPACE: C:` | `свободно 9,3 ГБ из 111,2` — цифры для разговора с клиентом |
| МЕДОК запущен, служба МЕДОК, Zillya, правила брандмауэра | таблицы без маркеров: пустой вывод и обрезанные `Status`/`Action` читались неверно | маркеры `MEDOC-RUN:`, `MEDOC-SVC: … status=Running`, `ZILLYA-SVC:`, `FW: … action=Block` |

**Что меняется на чужом железе.** В журнале гостя этой сессии ровно одно
изменение — `ipconfig /flushdns` (вердикт «изменение (подтверждение)»,
оператор подтвердил). Остальные 21 шаг — чтение. Это следствие политики, а не
дисциплины: `TestScenarioCommandsAllowedOnGuest` проверяет, что каждая команда
каждой проверки классифицируется как чтение на L1, и что каждая починка
попадает в белый список L2. Поэтому сценарии — это набор ограниченных чтений,
а изменения — только явные починки из меню. Крупные файлы и нехватка места
только показываются: агент ничего не удаляет и не «оптимизирует».

Открытый косметический дефект: вывод `nslookup` приходит в кодировке консоли
гостя и в архиве читается как `╤хЁтхЁ` (латиница и IP видны). На решение не
влияет; лечится переводом проверки на `Resolve-DnsName` (Win8+) с оговоркой
для Win7.

Сессия `bd3ffb`, DESKTOP-3DHVKKC (пользователь `Skif`, Windows 10 19041), 08:48:45–08:50:49,

Дефекты проверок (исправлены, закрыты тестами `TestScenarioMarkerRulesCatchLenovoOutput`
и `TestScenarioCommandsAllowedOnGuest`):

| проверка | что было | что стало |
|---|---|---|
| Служба МЕДОК Сервер | критерий — служба; на этой установке сервер держит порт **процессом**, службы нет → ложный отказ при живом сервере | проверка «МЕДОК Сервер запущен (процесс)» с маркером `MEDOC-RUN:`; служба — отдельная справочная проверка (`MEDOC-SVC:`) |
| Локальное подключение к 127.0.0.1:9996 | `Test-NetConnection … -InformationLevel Quiet` занял **84,29 с** (почти весь бюджет сессии, timeout 90) при живом сервере; на машине с фильтром Zillya сам пробный коннект ненадёжен | состояние соединений `Get-NetTCPConnection -LocalPort 9996` (`TCP: Listen` / `TCP: Established`, pid) — мгновенно и без пробного коннекта |

Урок про таймауты: 84 с — это не PowerShell, а, вероятнее всего, проверка пробного
коннекта фильтром антивируса. Поэтому правильнее убрать сам пробный коннект и читать
состояние TCP, а не увеличивать `timeout_sec`.

Отдельная находка при сверке файлов: txt-архив писал «Длительность: 2m4s», а заметка
в памяти — «3m5s» для той же сессии. Виновата служебная запись `/save`: она добавляется
уже после записи txt, и `duration()` считала время по ней. Исправлено (коммит `30c4a6f`),
закрыто тестом `TestArchiveDurationIgnoresSaveNote`: длительность — до последнего
реального шага.

## 8. Если запустить бинарь на госте нельзя

Тогда остаётся оффлайн-путь, и он у нас уже есть: на флешке лежит загрузочная Ubuntu
(`boot/`, `casper/`, `EFI/`, `dists/`). Загружаемся с неё на проблемном ПК и лечим диск без
работающей Windows. Для этого нужен **linux/amd64** бинарь — он теперь собирается:
`scripts/build-fast-agent.sh fast` кладёт `FastAgent/fastagent-linux-amd64` (и `FieldKit/`
подхватывает его в комплект). Осталось прогнать оффлайн-путь на живой x86_64-машине.

## 9. Риски

| риск | как снимаем |
|---|---|
| антивирус/Defender ругается на скачанный exe | файл приходит через AnyDesk-трансфер, не из интернета; в README-FIRST — шаги SmartScreen; не упаковываем, не обфусцируем |
| в корпоративной сети режут 443 наружу | тогда канал не поднимется; fallback — флешка физически + AnyDesk-трансфер, отчёт собирается локально |
| брокер на публичном Funnel увидят сканеры | вход по коду не отдаёт ничего без пары; сессия живёт 15 мин до pair; никакого перечисления кодов (`/fa/pair` считает лимит попыток) |
| оператор по ошибке подтвердит опасное | policycheck на госте + двойное подтверждение для VForbidden на L2; в консоли показывается вердикт и что именно будет выполнено |
| гость захочет аудита | журнал на госте виден и полон; сессию можно закрыть с любой стороны |

## 10. Открытые вопросы

1. Разрешать ли L3 в удалённом режиме? Предлагаю **нет** — L2 максимум, остальное только через
   физическое присутствие/оффлайн-загрузку. Это соответствует духу «чужой ПК».
2. Нужен ли веб-интерфейс оператора, или хватает консоли `-remote`? Начали с консоли —
   R1 показал, что для чтения её хватает; R3 (передача файлов) обошёлся консолью без веба.
3. Хранить ли архивы сессий на pi5 бессрочно? Предлагаю 90 дней, дальше — в Jev.
4. Публиковать ли `/fa/ticket/{code}.exe` без авторизации: удобно, но 6,4 МБ на каждый скачок;
   можно отдавать только с локального адреса и перетаскивать файл из `~/.cache/fastagent/`.
