# FastAgent — быстрый агент с регулируемым уровнем доступа

Параллельный агент для админской флешки (классический `Agent/` не изменяется и работает рядом).
Цели: **скорость** (облачный DeepSeek первым + стриминг) и **безопасность на чужом ПК**
(уровни доступа L0–L3 + журнал действий).

## Что внутри

| Решение | Зачем |
|---|---|
| Приоритет №1 — облачный **DeepSeek** (`https://api.deepseek.com/v1`, модель `deepseek-flash`) | Первый токен ~0.9 с, не требует gpu2/Pi/WoL |
| Локальная **Ollama (gpu2 через Pi-шлюз)** вторым провайдером | Резерв, когда нет интернета/лимит; включается автоматически |
| Стриминг (SSE) с печатью по мере поступления | Ощущаемая скорость: текст виден сразу, а не через 5–30 с |
| Таймаут «первого токена» (25 с) | Мёртвый провайдер отбрасывается быстро, без ожидания полного таймаута |
| Короткий системный промпт + обрезка истории (`history_limit`) | Меньше входных токенов → меньше latency и цена |
| Уровни доступа L0–L3 с белыми списками | Агент выполняет команды, но только разрешённые на выбранном уровне |
| Журнал действий `Data/logs/actions_<дата>.log` (JSON Lines) | Видно, что и с каким вердиктом запускалось |
| Слой знаний `/rag` (Jev), `--serve` (встроенный Web UI) | Память и интерфейс — внутри бинарника, без `curl`/`jq` на гостевом ПК |
| Декларативные инструменты + MCP-клиент | Модель просит `read_file`/`grep`/`glob`/`write_file` структурно, а не через регулярку |

## Уровни доступа

| Уровень | Название | Что выполняет |
|---|---|---|
| `L0` | chat | Ничего не выполняет — только диалог и объяснения (безопасно на любом ПК) |
| `L1` | read | Только чтение из белого списка, **без подтверждения**: `ipconfig /all`, `systeminfo`, `Get-*`, `Test-*`, `netstat`, `tasklist`, `nslookup`, `reg query`, `uname`, `df`, `journalctl`, `systemctl status`… |
| `L2` | fix | L1 + безопасные починки, **каждая с подтверждением `y`**: `ipconfig /flushdns`, `netsh winsock reset`, `Restart-Service`, `sfc /scannow`, `dism … /restorehealth`, `gpupdate /force`, `systemctl restart`… |
| `L3` | admin | Любые команды, подтверждение обязательно; **опасные — двойное** (`yes`): `format`, `diskpart`, `bcdedit`, `reg delete`, `del /f`, `Remove-Item -Recurse`, `shutdown`, `Set-ExecutionPolicy`, `rm -rf`, `mkfs`… |

Ключевые правила политики (`classify()` в `main.go`):

1. Порядок проверок: **опасное → изменяющее → чтение**. Иначе `ipconfig /flushdns` поймается общим `^ipconfig` и выполнится без подтверждения (эта регрессия закрыта тестом).
2. Незнакомая команда ниже L3 — не выполняется, агент прямо говорит: «нужен уровень 3».
3. Повышение уровня в рантайме требует ввода `yes` (защита от случайного `/level 3`).
4. На L0 не выполняется ничего, даже при подтверждении.
5. **Обёртки разворачиваются**: `powershell -c "Get-Service …"`, `cmd /c …`, `sudo …` классифицируются по внутренней команде (`sudo ip addr` — чтение, `sudo rm -rf /` — опасно). `powershell -EncodedCommand …` — непрозрачная нагрузка, всегда опасно (L3 + двойное подтверждение).
6. **Токены в белых списках заякорены** (`(\s|$)`): без этого `w` совпадал с `wscript script.vbs`, `tr` — с `truncate`. Конвейер в интерпретатор (`… | bash`, `… | powershell`) и `find … -exec/-delete`, `sed -i`, `xargs`, `rm -rf /` — опасные.
7. **Подтверждение не дано = отказ** (в т.ч. при EOF stdin) — fail-closed.
8. Очистка журнала `wevtutil cl` — опасная (уничтожение следов), а `wevtutil qe/gl/el` — чтение.

## Слой знаний (`/rag`): та же память, но без `curl` и `jq`

Field-путь к базе знаний раньше жил в `scripts/rag_query.bat` и требовал на гостевом ПК
`curl` и `jq`. На чужом ноутбуке их может не быть — и «память» молча переставала работать.
Теперь тот же запрос делает сам бинарник (только `net/http`, без внешних утилит):

```json
"rag": {
  "url": "http://192.168.11.111:8030",
  "graph_url": "http://192.168.11.111:8020",
  "execute": true
}
```

- `/rag <вопрос>` — роутер Jev: exact FTS5 отвечает за миллисекунды, синтез — около 10 с.
  В консоль печатается `источник=router strategy=… elapsed=…ms degraded=… decision_id=…`.
- `/rag graph <вопрос>` — LightRAG-граф напрямую. Только по явной просьбе: замерено
  22.09.2026, что на Espero-мануале граф медленнее (37 с против 10 с) и на том запросе
  ответил про другую тему. Автоматического fallback нет намеренно.
- `execute: false` — режим «только материал»: роутер не зовёт модель, ответ за миллисекунды
  (поле `context` вместо `agent_response`). Агент берёт `context`, если синтеза нет.

Найденная справка уходит в историю сообщением `Справка из базы знаний (…)`, поэтому модель
отвечает уже с её учётом. Недоступный Jev — это ошибка `[RAG]`, а не «ничего не нашлось»:
агент не притворяется, что памяти нет.

## Встроенный интерфейс (`--serve`): один файл — открылся чат

Подход llamafile («запустил — работает, браузер уже тут»), но с границей, которой у
llamafile нет и быть не может — он не исполняет команды на чужом ПК:

```bash
fastagent.exe --serve --port 8888          # http://127.0.0.1:8888
fastagent.exe --serve --token секрет       # то же, но доступ по токену
```

- `GET /` — страница чата, встроена в exe (`ui.html`, без внешних библиотек; открывается
  в Firefox Portable).
- `POST /api/chat` — вопрос → ответ; история держится в памяти процесса.
- `GET /api/diag` — снимок диагностики чтением, только при уровне L1+.
- `POST /api/report` — отчёт в `Data/reports/`.
- `POST /v1/chat/completions` — OpenAI-совместимый endpoint для Page Assist / Open WebUI.
  `stream:true` отдаёт **один** финальный чанк и `[DONE]` — это совместимо с клиентами, но
  не посимвольный поток; так и написано, а не «почти стриминг».
- Слушает только `127.0.0.1`. Без `--token` доступен лишь с localhost; с токеном —
  `Authorization: Bearer …` или `?token=…`.
- **В HTTP-режиме команды не выполняются.** Исполнение остаётся в консоли, где оператор
  видит подтверждение y/n. Иначе любой в той же сети получил бы исполнение команд на
  гостевом ПК.

## Декларативные инструменты и MCP (этап 10)

У llamafile правильно: модель не парсит оболочку, а просит инструмент **структурно**.
Здесь так же: декларации уходят в `tools` OpenAI API, вызовы собираются из
`delta.tool_calls` по `index`; если провайдер tools не умеет (HTTP 400/422), запрос
повторяется без деклараций, и модель возвращает JSON-конверт:

```tool
{"name":"read_file","arguments":{"path":"C:\\Windows\\win.ini"}}
```

| Инструмент | Уровень | Что делает и где граница |
|---|---|---|
| `read_file` | L1 | строки с номерами; 64 КБ / 2000 строк; бинарные и секреты — отказ |
| `grep_search` | L1 | рекурсивный поиск RE2; 15 с, 500 совпадений; `.git`/бинарники пропускаются |
| `file_glob_search` | L1 | `**/`; до 500 результатов |
| `write_file` | L2 + `y` | 1 МиБ, атомарно (`.tmp-fastagent` + rename); системные каталоги и секреты запрещены |
| `mcp__<сервер>__<tool>` | **L3** + `y` | внешний процесс по MCP stdio; чужой инструмент не классифицирован, поэтому только L3 |

Цикл: до 6 шагов, повторный вызов с теми же аргументами отклоняется, результат уходит
сообщением `role=tool` в JSON `{"ok":…}` — отказ политики не выглядит успехом. Обрезка
истории не отрывает `assistant(tool_calls)` от его `tool`-ответов.

MCP-серверы подключаются в конфиге (запускаются при старте, ошибка не фатальна):

```json
"mcp": {"servers": [{"name": "filesystem", "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-filesystem", "/tmp"]}]}
```

Неинтерактивный ход для скриптов и проверок: `fastagent.exe -ask "вопрос"`.

Живые прогоны 13.11.2026 (DeepSeek):
- L1: `read_file` вернул маркер файла; `file_glob_search` + `grep_search` отработали в одном ходе, ttft 0.46 с.
- L2: `write_file` → `[tool] write_file … (изменение (подтверждение))` → `Записать файл? (y/n)` → `y` → `записано 32 байт`; в журнале строка `tool:write_file`, `verdict=изменение (подтверждение)`, `approved=true`.
- `-ask` на L2: `write_file` отклонён — «нужно подтверждение оператора, но сессия неинтерактивная» (это правильный отказ: в `-ask` человека нет).
- `-policycheck` → `26/26 OK`; `-selftest` на L2 → `6/6 OK` (отказы записаны в журнал).

**В HTTP-режиме (`--serve`) инструменты не выполняются** — граница этапа 9 не меняется.

## Удалённая диагностика (R1–R3): гость звонит сам, ключи остаются у оператора

Сценарий — `../REMOTE-DIAG.md`. Коротко: на проблемный ПК попадает **один** бинарь, он сам
звонит на брокер (pi5, Tailscale Funnel), а оператор работает в своём терминале. AnyDesk нужен
только перетащить файл и запустить его. Три процесса — три режима одного бинаря:

```bash
# 1) на pi5: брокер (реле, ключа подписи не знает)
fastagent -broker -broker-addr 127.0.0.1:8866           -broker-secret <секрет> -ticket-exe FastAgent/fastagent.exe

# 2) на pi5: оператор — создаёт сессию, получает код и файл-билет
fastagent -remote new -broker-url https://pi5.tail823290.ts.net/fa -broker-secret <секрет>
#    Файл-билет: ~/.cache/fastagent/fastagent-<код>.exe  (перетащить в AnyDesk)
#    Одна команда без REPL: -remote-cmd "read C:\Windows\win.ini"

# 3) на госте: двойной щёлчок по fastagent-<код>.exe (он и есть -link);
#    если имя переименовали — fastagent.exe -link и ввести код
```

Что можно: **чтение** — `diag`, `read`, `grep`, `glob` (R1), **`run <команда>`** (R2),
**передача файлов** — `get`/`put` до 50 МиБ кусками по 256 КиБ (R3). Консоль оператора
понимает `read <путь>`, `grep <шаблон> [каталог] [glob]`, `glob <шаблон> [каталог]`,
`run <команда>`, `get <путь на госте> [локальный]`, `put <локальный> <путь на госте>`,
`help`, `quit`. `write_file` удалённо не выполняется: `remoteExec` пропускает инструмент
только через `classifyTool(kind, L1Read)`; запись идёт отдельным `put_file` и только после
подтверждения оператора.

`run` исполняется по политике **гостя** (уровень в этом режиме — L2, не выше): чтение идёт сразу,
изменяющая команда двухшаговая. Гость возвращает `needs_approval` с вердиктом, консоль
спрашивает `y/n` у оператора, и только потом уходит та же команда с `approved=true` и **другой
подписью** — `approved` входит в каноническую строку, поэтому реле не допишет подтверждение.
Опасное (`rm -rf /`, `format C:`) и «вне белого списка» отклоняется на L2 даже с `approved`:
L3 удалённо не разрешён. Без терминала (stdin не tty) `confirm` честно отказывает — автонет.

Почему это не «дыра в HTTP-запрете» (граница этапа 9 держится):

- **ключа модели на госте нет** — модель и Jev работают у оператора, гость возвращает только
  результат; брокер — реле, команды подписаны `HMAC-SHA256` сессионным ключом из кода и
  guest-токена, поэтому даже скомпрометированный брокер не подделает команду;
- **политика на госте своя**: вердикт считает `classifyTool`, отказ при несовпадении подписи
  тоже на госте (`[link] ОТКАЗ: подпись команды … не сходится`);
- сессия 2 ч, окно пары 15 мин, простой 15 мин, токен только в памяти, автозапуска и службы нет;
- журнал гостя — отдельный файл `Data/logs/actions_remote_<дата>.log` с `provenance=remote`
  и честным `approved` (флаг берётся из подписанной команды, а не выводится из вердикта).

Живые прогоны 18.11.2026 (pi5):
- R1: `diag` → 0.07 с; `read /etc/hostname` → `1: pi5`; `GET /fa/ticket/<код>.exe` отдал бинарь
  9 000 174 Б с именем `<код>` в `Content-Disposition`; в журнале `link-start`, `diag`,
  `tool:read_file` — все `approved=true`, `verdict=чтение`.
- R2: `run uname -a && id` → `exit=0` за 0.01 с без вопроса; `run ipconfig /flushdns` + `y` →
  вердикт «изменение (подтверждение)», `exit=127` (на Pi команды нет), в журнале `approved=true`;
  `run netsh winsock reset` + `n` → «Отменено оператором», в журнале только «ждёт подтверждения».
- R3: `get /etc/hostname` → 4 Б, `sha256` сверен; `put` 3 МиБ (3 145 728 Б) → `needs_approval`,
  `y`, записано **за 3.0 с** (12 кусков), `sha256` на госте совпал до байта, в журнале 12 записей
  `approved=true`; `put` с `n` → «Отменено оператором», файла нет. Двойной щёлчок по
  `fastagent-<код>.exe` сам включает `-link` (по имени файла).

## Комплект для тестирования (FieldKit)

Папка `FieldKit/` на флешке — то, что нужно взять на гостевой ПК и что удобно
передать без всего репозитория. Собирается из текущего дерева на Pi:

```bash
bash scripts/make-fieldkit.sh            # -> FieldKit/ (или FieldKit-YYYYMMDD-HHMM/)
```

Состав (ключи не копируются — только образец):

| Файл | Зачем |
|---|---|
| `fastagent.exe` | windows/amd64, собран из текущего HEAD |
| `fastagent-linux-arm64` | отладка на Pi5 (aarch64), брокер и гость R1–R3 |
| `fastagent-linux-amd64` | оффлайн-путь: загрузочная Ubuntu на x86_64 |
| `config.fast.example.json` | образец конфига: скопировать в `Data\config.fast.json` и вписать ключ |
| `README-FIRST.txt` | порядок действий и что прислать после теста |
| `README.md`, `FastAgent-README.md` | полная документация |
| `RUN-FIELD-TEST.txt`, `FIELD-TEST.md` | сценарий полевого теста и чек-лист ожиданий |
| `tests/`, `scripts\field-test-fastagent.bat` | входные файлы 8 сессий и прогонщик |
| `SHA256SUMS.txt` | контрольные суммы бинарников и документов |

На гостевом ПК: `START.bat` → **[7]** (или `scripts\field-test-fastagent.bat`).

Пятый дефект, найденный во втором прогоне и устранённый: `systeminfo | findstr /C:"OS Name"`
вернул `Windows 10 IoT ????????????? LTSC` — консоль в UTF-8 (наш `chcp 65001`) заставляет

заметила и написала об этом в ответе). Решение: команды разделены по типу — синтаксис
PowerShell (`Get-*`, `@{…}`, конвейеры с cmdlet'ами) идёт в `powershell`, нативные утилиты

с переключением `chcp <OEM> … chcp 65001` вокруг команды: кириллица снова читается, а наш
UTF-8-интерфейс не портится. Код возврата снимается до возврата кодировки.

> (у `sc` свои капризы с пробелами после `=`), политика тут ни при чём — в журнале вердикт `чтение`,

6. **Агент врал модели о коде возврата.** В историю диалога уходил жёстко зашитый

   раньше модель вообще не знала, что команда не запускалась, и предлагала её повторно.
7. **`findstr` по английским подписям на русской Windows не находит ничего.** Под OEM-кодировкой

   локалью-независимыми командами: `wmic os get Caption,Version,BuildNumber,OSArchitecture /value`,
   `Get-CimInstance Win32_OperatingSystem`, `ver`, `systeminfo` без фильтра; в `/diag`-снимок
   добавлены `wmic os` и `wmic logicaldisk`. Плюс правило «код != 0 или пустой вывод → не утверждать успех».
8. **Обрезка вывода рвала многобайтные символы.** `truncate` резал строку по байту, и на стыке

   видно, сколько символов потеряно: `…[обрезано 12 симв.]`.

   и это было перенесено на прогон 3, хотя там агент запускался **от администратора**, а `sfc`/`dism`
   оператор просто отклонил (данных нет вовсе). Первоисточник — прогон 1: DISM сам напечатал

   уровня целостности (`S-1-16-12288` High = повышен, `S-1-16-8192` Medium = обычное окно) —
   это не зависит от языка системы (названия групп локализованы, SID — нет). В шапке появляется

    потоки ошибок и прогресса в служебный XML: `#< CLIXML`, `<Objs Version="1.1.0.1" …>`, пачки
    `<AV>Preparing modules for first use.</AV>` и текст ошибок с escapes `_x000D_` и удвоенными
    обратными слэшами (`C:\\путь\\к\\mycustomtool.exe`). В отчёт прогона 7 это попало дважды
    (2 блока, 16 XML-записей), модель даже объясняла оператору «CLIXML-обёртка — это не ошибка».
    Теперь вывод проходит через `stripCLIXML`: progress-записи выбрасываются целиком, а ошибки
    восстанавливаются человеческим текстом с меткой `[stderr]` (14 строк из реального отчёта
    прогона 7), escapes и удвоенные слэши разбираются. Закреплено `clixml_test.go` на настоящих
    образцах прогона 7, включая прогон по всему отчёту целиком.
16. **У sfc/dism не было шансов доработать: общий таймаут 120 с.** `sfc /scannow` и
    `dism /restorehealth` идут 5–40 минут, поэтому при общем таймауте они обрывались бы строкой
    `[timeout]` — данных по ним не было бы вообще. Добавлен `commandTimeout`: для
    `sfc`/`dism`/`chkdsk`/`vssadmin`/`cleanmgr` таймаут поднят до 45 минут (обёртки `cmd /c "…"` и
    `powershell -c "…"` разворачиваются, иначе длинного таймаута не будет), и оператор видит
    `[i] длинная операция: таймаут поднят до 45 мин`. В полевой тест добавлена шестая сессия
    **L2-sfc** (`tests/field-L2-sfc.txt`): она прямо просит `sfc /scannow` и
    `dism /online /cleanup-image /restorehealth` — последняя дырка в покрытии закрывается не
    надеждой на инициативу модели, а заданием.

### Восьмой полевой прогон — sfc/dism выполнены впервые; найдены UTF-16 и «отрезанный итог»

Шесть сессий, все на месте. Самопроверки: `26/26 OK` + три блока `6/6 OK`. Кодировки: псевдографики,
`?` и U+FFFD — по нулям. Журнал: 41 запись в окне своего прогона (`19:04–19:12`). Живая блокировка
снова получена: модель предложила `wevtutil sl System /ms:67108864 /rt:true`, политика L2 отсекла
(`[BLOCK] Команды нет в белом списке`).

**Дефект 16 подтверждён в поле.** Сессия L2-sfc отработала то, ради чего её добавляли:

```
[cmd] sfc /scannow  (изменение (подтверждение))
      Запустить? (y/n):   [i] длинная операция: таймаут поднят до 45 мин …
      -> код 0, 247.46 с
[cmd] dism /online /cleanup-image /restorehealth  (изменение (подтверждение))
      Запустить? (y/n):   [i] длинная операция: таймаут поднят до 45 мин …
      -> код 0, 191.56 с
```

Ни `[timeout]`, ни `740`. Пять прогонов данных по этим командам не было вообще — теперь есть.

17. **`sfc` пишет UTF-16LE, а не OEM.** sfc.exe — Unicode-приложение: в pipe он отдаёт пары байт, и
    однобайтовая таблица cp866 превращала его вывод в мешанину
    (`\x1d\x040\x04G\x040\x04B\x04>\x04 …` вместо «Начато сканирование системы…»). DISM пишет обычный
    OEM и читался нормально — поэтому дефект и не всплывал, пока не пришла sfc. Добавлен `decodeUTF16`
    (BOM + структурный признак: у ASCII-символов старший байт нулевой, то есть нули стоят строго через
    один — на нечётных позициях у LE, на чётных у BE) с проверкой результата на осмысленность. Он
    работает **до** проверки `utf8.Valid`, иначе ASCII-часть UTF-16 прошла бы как «нормальный вывод» —
    с NUL-байтами внутри. Те же байты из отчёта прогона 8 теперь читаются как
    «Начато сканирование системы.  Этот процесс может занять некоторое время.».
18. **Итог долгой команды отрезался, а строки прогресса съедали бюджет.** `truncate` оставлял только
    начало вывода, а вердикт у sfc/DISM печатается ПОСЛЕДНИМ («Проверка 100% завершена. Защита
    ресурсов Windows не обнаружила нарушений целостности», «Восстановление выполнено успешно»).
    Из-за этого 4 минуты работы sfc дали модели только служебные строки — и модель сама честно
    написала, что итога нет, и попросила CBS-лог. Плюс сотни строк прогресса sfc/DISM занимали весь
    лимит. Теперь: `truncate` сохраняет начало (1/3) и конец (2/3) с пометкой о пропущенной середине;
    `collapseProgress` сворачивает подряд идущие строки прогресса (`Проверка 12% завершена.`,
    полосы DISM `[====  12.7%  ]`) в одну с пометкой «пропущено N строк прогресса»; `normalizeOutput`
    приводит одиночные CR к LF и убирает NUL. На реальном фрагменте прогона 8: было 86 строк
    мешанины, стало 10 строк читаемого текста.

### Девятый полевой прогон — итоги sfc/dism читаются; найдены «осиротевший маркер» и несвёрнутый прогресс DISM

Шесть сессий, самопроверки `26/26 OK` + три `6/6 OK`, журнал 45 записей только своего прогона
(19:33–19:40), псевдографика 0, `?` внутри русских слов 0, U+FFFD 0, NUL 0.

**Главное — дефекты 17 и 18 закрыты на живых данных.** Сессия L2-sfc впервые дала читаемый результат:

| Что | Прогон 8 | Прогон 9 |
|---|---|---|
| Вывод sfc | пары байт `\x1d\x04G\x04…` | `Начато сканирование системы.  Этот процесс может занять некоторое время.` |
| Итог sfc | отрезан | `Проверка 100% завершена.` + `Защита ресурсов Windows не обнаружила нарушений целостности.` |
| Строки прогресса sfc | 197 строк забили вывод | `…[пропущено 197 строк прогресса]…` |
| Итог DISM | отрезан | `Восстановление выполнено успешно. Операция успешно завершена.` |
| Время / код | 247.46 с / 0 (sfc), 191.56 с / 0 (dism) | 175.31 с / 0 (sfc), 144.90 с / 0 (dism) |
| Модель про итог | «итоговой строки нет, нужен CBS-лог» | «обе команды — код 0, хранилище компонентов в порядке» |

19. **«Осиротевший» маркер `#< CLIXML`.** XML-блок вырезался, а маркер оставался отдельной строкой —
    7 раз за прогон. Причин две: (1) PowerShell печатает маркер и отделяет его от `<Objs>` ПУСТОЙ
    строкой, а шаблон допускал ровно один перевод строки; (2) на CRLF-выводе `(?m)$` стоит перед
    `\n`, а перед ним остаётся `\r`, который не покрывался `[ \t]*`. Исправлено: шаблон блока
    допускает пустые строки между маркером и XML, шаблон маркера — `\r?` и ведущие пробелы, а
    нормализация строк в `finalizeOutput` идёт **до** разбора CLIXML. Пакеты пустых строк после
    вырезания маркеров схлопываются.
20. **Полосы прогресса DISM не сворачивались вообще.** DISM печатает после каждой полосы пустую
    строку, поэтому серия распадалась на серии по одной полосе — а «серия из одной строки» не
    сворачивалась. В отчёте прогона 9 это 4023 символа полос, которые выдавили из вывода всё
    остальное (журнал: вывод DISM 1980 символов против 252 у sfc). Теперь пустые строки внутри
    серии прогресса считаются её частью. На настоящем отчёте прогона 9 обработка сжимает
    `field-L2-sfc` с 7178 до 3707 символов, а десять полос — до одной пометки плюс свежая строка.

Плюс к этому: в системный промпт добавлено правило про пустой вывод — «пустой вывод при коде 0 это
не факт о системе, а отсутствие данных: проверь то же самое ДРУГИМ инструментом». Повод реальный: в
L1 модель спросили про состояние сетевых адаптеров, `Get-NetIPConfiguration` вернул пусто при коде 0,
и агент честно пометил `[i] вывод пуст при коде 0 — данных нет`; контрольная команда в тесте
(`ipconfig /all`/`Get-NetAdapter`) добавлена в `tests/field-L1.txt`. В тест L2-blk добавлена строка,
где оператор настаивает на выполнении `wevtutil cl System` — живая блокировка не должна зависеть от
того, решит ли модель отказаться самой.

## Известные ограничения

- Стриминг: печать `AI > ` начинается до проверки провайдера, поэтому при fallback строка `[fallback]` идёт после первого `AI >` — косметика.
- `auto_followup` добавляет второй (и последующие) запрос к модели — при экономии токенов выключается `/follow off`.
- Политика работает по белым спискам (regex) — если нужной команды нет в списке, добавьте её в `reReadSafe`/`reFixAllowed` и запустите тесты.
- На Linux команды исполняются через `/bin/sh -c`, на Windows: нативные утилиты — через `cmd.exe` с временным `.cmd` (там переключается кодовая страница), команды PowerShell — через `powershell -NoProfile -NonInteractive -EncodedCommand` (Base64/UTF-16LE), чтобы текст скрипта никто не переписывал по дороге.
- Собственная обёртка модели `powershell … -Command "…"` снимается перед запуском (иначе получается вторая оболочка, которая раскрывает `$переменные`); оператор видит это строкой `[i] обёртка powershell снята, выполняется: …`.
- Инструменты: `write_file` и MCP требуют интерактивного `y`; в `-ask` подтверждений нет, поэтому запись и MCP там отклоняются (это честно, а не «не успели»).
- MCP-инструменты видны только на L3: их семантику задаёт чужой сервер, и классифицировать её нашей политикой нельзя.
- В `--serve` инструменты не выполняются — HTTP-граница этапа 9 сохранена.
